# Disputed points and chosen defaults

| # | Debate | Side A | Side B | Recommended default and why |
|---|---|---|---|---|
| 1 | argparse vs click vs typer | **argparse:** zero dependencies, fastest import (about 4 ms measured) [S47]. "Sufficient for most needs" [S1]. Package authors on r/Python avoid the extra dependency [S59]. 3.14 adds colored help and `suggest_on_error` [S6]. | **click/typer:** less boilerplate, CliRunner, completion, consistent conventions [S18, S33]. Typer gives type-hint ergonomics [S1, S32]. The cost is import time (about 120 ms for click, 200 ms for typer, measured) and transitive deps; in large click apps the whole codebase gets imported [S47]. | **Converting argparse scripts:** stay on argparse. The rewrite risk isn't worth it, and agents know argparse well. **New multi-command tools:** click (or typer if the team wants type hints), with lazy imports. Measure with CLI-10. |
| 2 | src vs flat layout | **src:** prevents shadowing and catches missing package data [S2, S21]. PyPA guide [S1], ToB [S24], uv `--package` default. | **flat:** simpler; the CLI runs from the source tree without installing [S2]. Fine for small or unpublished tools [S27 decision tree]. Practitioners report "zero consensus" [S59]. | src for anything with `[project.scripts]`. In convert mode a flat layout is acceptable **only if** TST-03 runs in CI, because that test catches what src would have prevented. |
| 3 | Delete requirements.txt? | **Delete it:** pyproject plus `uv.lock` are the source of truth; "don't introduce new requirements.txt files" [S28]; ToB migration deletes them [S24]. | **Keep a pip path:** many users and platforms (Docker, Lambda, corporate pip mirrors) expect one. `uv export` exists for exactly this [S12], including the PEP 751 `pylock.toml` standard [S59]. | Delete hand-written requirements files, but document `pip install .` / `pipx install`. If a pinned file is needed, generate it with `uv export` and diff-check it in CI (DEP-04). |
| 4 | Commit `uv.lock` for libraries? | Apps commit it; libraries may gitignore it [S25]. | Committing it everywhere gives reproducible CI [S8]. | A CLI is an app, so commit it. But the lock does not reach `uv tool install` or pipx users [S14], so also test fresh resolution (DEP-03). |
| 5 | Exit code scheme | **Minimal:** 0 / 1 / 2 (usage), "don't get clever" [S48, S16 "map non-zero codes to the most important failure modes"]. | **Semantic, sysexits-like:** 3 not found, 4 permission, 5 conflict, 75 transient, 78 config [S30, S37]. | Always use 0/1/2. Add more codes only for failure classes a caller would branch on (not-found, conflict, transient), and document them. Extra codes cost little, but undocumented ones are noise. |
| 6 | Secrets in env vars | **No:** env vars leak through `ps`/`/proc` and child processes; use files, stdin, or IPC [S16]. | **Env vars are fine:** they are the standard for CI and containers [S30]. | Accept a `--token-file` or stdin. Allow a `TOOL_TOKEN` env var for CI convenience, and document the trade-off. Never accept a flag value (CFG-03). |
| 7 | Automatic JSON when piped vs only with `--json` | **Auto:** detect non-TTY and emit machine-readable output [S30]. Agent-first tools go further: JSON is the only format [S58, S62]. | **Explicit only:** TTY detection decides color and animation, not the format. Scripts opt in with `--json`/`--plain` [S16, S39 (gh prints plain line-based text unless `--json`)]. | Explicit `--json`. A format that changes silently surprises people debugging with `| less`. Piped output stays plain text with no ANSI. |
| 8 | Where structured errors go in `--json` mode | stdout, as an error envelope, so one parser handles both cases [S30]. | stderr, keeping stdout for data only [S16, S17]. | Write the JSON error to **stderr** and exit non-zero. Agents see both streams, and the stdout-is-data rule stays absolute. Document the choice whichever way it goes. |
| 9 | Prompts at all? | "Prompt if you can" when stdin is a TTY [S17]; "prompt for missing input, but never require" [S16]. | Agent-first: non-interactive by default [S36]; "never require interactive input" [S30]. | Prompting when stdin **and** stdout are TTYs is fine, as long as every prompt has a flag (AGT-05) and nothing prompts without a TTY (AGT-04). |
| 10 | Silent success vs confirmation | Unix tradition: silence means success. | Brief confirmation, `--quiet` to suppress [S16, S30]. better-cli [S30] and joelclaw [S58, S62] put "next actions" in every output. | Print a brief confirmation for mutations. "Next steps" hints only as an opt-in or in errors, because they cost tokens on every call. |
| 11 | CLI vs MCP for agents | CLI: `--help` is cheap in tokens [S19]; composes with `jq`/`head`; models already know common CLIs [S53]. In a 500-trial eval, correctness was equal but a thin MCP wrapper cost about 6x more on complex tasks [S50]. | MCP: wins when a task maps to one endpoint [S50]; better for remote or proprietary tools, OAuth and enterprise access control, stateful sessions, and non-technical users [S37, S50, S53]. | Build a good CLI first and ship a short usage guide with it (DOC-06), because the model has not seen your CLI before. Add an MCP server when users need OAuth, remote access, or no shell. |
| 12 | Detecting agents through env vars | Lets the CLI switch to machine mode automatically [S38]. | The variables are unauthenticated, names have not converged, and they are an injection surface [S38]. | Use detection for cosmetics only. Explicit flags remain the contract (AGT-13). |
| 13 | `requires-python` floor | Modern floor (>=3.11) for modern tooling [S24]. | The lowest version you can support and test. Never cap [S22]. | Set the floor to the oldest version in the CI matrix, and write down why (for example, needs `tomllib` → 3.11). No cap. |
| 14 | Startup budget | Under 50 ms [S31]. | 100–500 ms is "fast enough" for scripting languages [S17]. | Aim for ≤ 300–500 ms for `--help` in Python. 50 ms is not achievable with click or typer [S47]. |
| 15 | Build backend | `uv_build` is simpler and sufficient [S24]. | hatchling or setuptools have plugins, setuptools-scm, and extension support [S27]. | `uv_build` for pure-Python CLIs in uv projects. Use hatchling with hatch-vcs if you want git-tag versions. |
| 16 | Structured input: flags vs one JSON payload | **JSON payload:** nested data maps cleanly; repeated flags for groups are ambiguous. | **Flags:** measured 5/5 correct for every model vs 2/5–3/5 for small models with JSON input, at 4–11x lower cost; JSON fails on shell quoting [S57]. | Flags. Offer JSON input only as an extra, read from a file or stdin (AGT-15). |

## Open questions

Areas with no settled answer. Treat the defaults here as judgment calls and re-check them when the tooling changes.

1. **Locked installs for end users.** `uv tool install`, pipx, and pip resolve dependencies fresh and ignore `uv.lock` [S14, S15]. Until tools install from a lock, keep `pyproject.toml` ranges correct and test the lowest direct versions (DEP-03).
2. **Windows behaviour.** CLI design guides rarely cover UTF-8 output when piped on Windows, `.exe` shims created for entry points, or how TTY detection differs between Git Bash/mintty and Windows Terminal. OUT-12 rests on Python's own encoding rules.
3. **argparse exits inside `main(argv)`.** argparse calls `sys.exit` on `--help` and on usage errors, and `exit_on_error=False` covers only some errors. Tests should expect `SystemExit` (TST-02); see [patterns.md](patterns.md).
4. **Exit-code and JSON-error standards.** None exists. Pick a scheme, document it, and keep it stable (#5 and #8 above).
5. **Agent-detection env vars.** Names such as `AGENT`, `CLAUDECODE`, and `CODEX_*` are community conventions, not a standard [S38].
6. **Token budgets.** Sources agree output should be small and bounded but give no measure. A practical check: the default `list` call should fit in a few kilobytes and say how to get more.
7. **Keeping lazy dispatch cheap.** A useful extra test: run `tool --help` in a subprocess and assert heavy modules are absent from `sys.modules`.
