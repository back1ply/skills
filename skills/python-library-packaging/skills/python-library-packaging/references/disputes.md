# Disputed points

Where sources disagree. The SKILL.md defaults follow the last column. Item IDs point to [checklist.md](checklist.md).

| # | Debate | Side A | Side B | Recommended default and why |
|---|---|---|---|---|
| 1 | Upper caps on dependencies | **Cap rarely:** "Do not cap by default", only on known or >75% likely breakage [S10]. "Don't ever pin major versions, unless you know they're broken" [S26]. | **Cap at known majors:** pyOpenSci allows caps "sparingly" when you know where compatibility ends (`pandas>=1.0,<3.0`) [S12]. The awesome-copilot skill shows `httpx>=0.24,<2.0` and `requests>=2.28,<3.0` as "acceptable" [S49]. | No caps by default. A cap needs a comment and a known incompatibility (DEP-02). The exceptions S10 lists (framework plugins, packages released in lockstep) are fine. Users can add a missing cap, but they cannot remove one you added. |
| 2 | Python floor policy | **SPEC 0:** drop a Python version 3 years after release. As of 2026 Q4 that means a 3.13 floor [S14]. | **All CPython-supported versions:** 3.11 through 3.15 today (5-year support) [S15]. This view appeared only in a GitHub comment seen through search, so it is weak as a source. | Scientific or numerical libraries that depend on the NumPy stack: SPEC 0. General-purpose libraries: support every non-EOL CPython (floor 3.11 until 2027-10). Either way, write the policy down (PY-01). |
| 3 | Commit the lockfile in a library repo | ToB migration checklist: libraries may skip it (CLI research S25). | pyOpenSci: commit a lock (`pylock.toml`) for mature libraries with CI [S12]. A lock gives reproducible CI. | Committing is fine and helps CI stay reproducible. It never protects users, so DEP-04 and DEP-05 are required either way. |
| 4 | Always add `NullHandler` | Common folklore and many templates add `logging.getLogger("pkg").addHandler(logging.NullHandler())` unconditionally. | The logging docs say WARNING+ reaching stderr when the app has no config "is regarded as the best default behaviour". NullHandler is only for when you deliberately want silence [S28]. | Don't add it by default. Warnings from your library should be visible to unconfigured apps. Never add any other handler (BEH-02). |
| 5 | DeprecationWarning vs FutureWarning for library deprecations | DeprecationWarning is the documented category for "other Python developers" [S23]. Type checkers also flag `@deprecated` [S22]. | DeprecationWarning is hidden by default unless triggered in `__main__`, so notebook or script users of a library may never see it. FutureWarning is shown by default [S23]. Some large libraries use FutureWarning for that reason (practice, not read in a primary source this pass). | DeprecationWarning for API removals (developers see it under `-W error` and pytest). FutureWarning only for changes in default behavior that affect results, which end users must notice. |
| 6 | `py.typed` in every subpackage? | PEP 561: the marker "applies recursively". Top level is enough [S5]. | Scientific Python guide: "add empty `py.typed` files to all packages/subpackages" [S39]. | Top level only (the spec). Extra markers do no harm, but they are not required. |
| 7 | SemVer vs CalVer | SemVer requires a declared public API, and a major bump signals breaking changes [S25]. | Hynek: SemVer cannot prevent breakage (Hyrum's Law), applying it is "entirely optional", and CalVer is fine [S26]. | SemVer for most libraries, because downstream tools and readers expect it. CalVer is acceptable with a written deprecation window (DEPR-05). Either way, the changelog says which scheme is used (DEPR-08). |
| 8 | Sphinx vs mkdocstrings | Sphinx: mature, intersphinx, autodoc from imports [S40]. | MkDocs + mkdocstrings: Markdown, easy plugins, but MkDocs' future is uncertain and the ecosystem is moving to ProperDocs or Zensical [S40]. | Sphinx + MyST for new libraries until Zensical stabilizes. Existing mkdocstrings sites can stay, with ProperDocs as the drop-in path. |
| 9 | Re-export style in `__init__.py` | `__all__` list [S7, S2]. | Redundant alias `from ._x import Y as Y` [S2, S3, S8]. | Use both: redundant aliases for the imports and `__all__` for the declared list. Ruff, pyright, and readers all agree then. |
| 10 | Eager convenience imports in `__init__.py` | Re-export everything at the top so users write `pkg.Thing` (common practice). | Importing any submodule runs all parent `__init__`s. That costs import time and invites circular imports [S7]. | Re-export the core public names. Keep heavy or optional subpackages as explicit `import pkg.sub` imports, or load them lazily (BEH-10). |
