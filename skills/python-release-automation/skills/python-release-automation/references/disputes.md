# Disputed points

Where sources disagree. The SKILL.md defaults follow the last column. Item IDs point to [checklist.md](checklist.md).

| # | Debate | Side A | Side B | Recommended default and why |
|---|---|---|---|---|
| 1 | Static version vs version from git tags | **Static + `uv version --bump`:** works with uv_build, readable in `pyproject.toml`, and a shallow clone can't change it (S6, S7, L1). | **Dynamic (hatch-vcs / setuptools-scm):** the tag is the only source, so tag and version can never disagree. Every commit gets a unique dev version (S29, S30). | Static for uv_build projects (the uv-first default of the sister skills). Dynamic is fine on hatchling/setuptools if VER-04 and VER-05 are enforced. Either way, GATE-02 checks version == tag. |
| 2 | Tag push vs GitHub Release `published` as trigger | **Tag push:** what PyPA's guide and Pradyun use. A tag ruleset protects it (S28, S47). | **Release published:** Scientific Python's default. The release UI is the single action, and watchers are notified (S42). | Either, with exactly one publish trigger (TRIG-01). Solo maintainers: `release: published` is one click and guarantees POST-01. Bot-driven repos: whatever the bot creates, publishing inside the same workflow (TRIG-04). Under immutable releases, `published` + uploading assets afterwards breaks (PROV-03). |
| 3 | Build and publish in one job vs separate jobs vs separate workflows | **One job:** Simon Willison's TIL builds and publishes in the deploy job (S46). | **Separate jobs** (PyPA calls building in the publish job "unsupported", S27, S28, S43). **Separate workflows** (Brett Cannon, crediting Seth Larson, S44). | Separate jobs in one top-level workflow (GATE-03). Separate workflows add artifact-passing complexity (`workflow_run` runs in default-branch context, S9) for little gain at small scale. Simon's pattern predates the attestation and isolation advice. |
| 4 | Changelog: hand-written vs fragments vs from commits | **Hand-written** Keep a Changelog: best prose, easy to forget. | **Fragments** (towncrier, scriv): no merge conflicts, enforced per PR (S31, S32). **From commits** (git-cliff, cz, PSR, release-please): zero extra files, but output quality equals commit discipline (S33–S38). | Solo or small: hand-written plus CHG-01 gate. Many contributors: towncrier with `check` in CI. Commit-derived only with enforced Conventional Commits and a human edit (CHG-04, CHG-05). |
| 5 | Fully automated release bots vs manual bump PR | **release-please / PSR:** version and changelog computed, release PR is the approval point (S35, S36). | **Manual:** `uv version --bump`, edit changelog, merge, tag. No PAT, no write-permission bot, no PR-creation setting (S15, S37). | Manual for solo maintainers (TRIG-09). Bots pay off with frequent releases and many contributors who already use Conventional Commits. |
| 6 | Required reviewer for a solo maintainer | Approval adds friction and can't stop the maintainer themselves; "prevent self-review" would block them (S11). | PyPI, PyPA, SPEC 8, and Brett all recommend an approval gate. It stops unintended triggers and makes a stolen-session release a two-step act (S24, S28, S43, S44). | Keep the environment with a reviewer even if solo (GATE-06). It costs one click per release. Turn off admin bypass. |
| 7 | Pinning actions to SHA vs version tags | The PyPA action's own examples use `@release/v1`. Scientific Python uses `@v4`-style tags (S27, S42). | SPEC 8 says "must be pinned using the full commit SHA". zizmor hash-pins everything by default. Brett adds the repo-level enforcement (S43, S39, S44). | SHA pins plus Dependabot with cooldown (SEC-06, SEC-07). Tag pins are the documented minimum, not the recommendation. |
| 8 | GitHub artifact attestations in addition to PEP 740 | Scientific Python adds `actions/attest@v4` to the publish job (S42). hynek's action offers it (S41). | PyPI already publishes PEP 740 attestations by default, verifiable with `pypi-attestations` (S26, S27). A second system adds permissions and another verify path. | Optional (PROV-02 NICE). Add it when you also ship artifacts outside PyPI (GitHub release assets, binaries). Standalone Sigstore signatures on the GitHub release are a further optional step, not researched this pass (gap 6). |
| 9 | Yank vs delete a bad release | PEP 592 and PyPI docs: yank, deletion breaks pinned users and is permanent (S2, S3, S4, S5). | Ultralytics postmortem: "Delete known-bad releases from PyPI" (S45). | Yank for broken or incompatible releases (PUB-05). Delete only malicious or compromised files (PUB-07). |
| 10 | Bump to `.dev0` right after a release | Makes local builds distinguishable from the release and mirrors what VCS versioning does (L4). | Adds a commit per release and confuses `uv version --bump` later (`.dev1 → .post1`, L3). | Optional (POST-04). Skip it with static versions unless you publish nightlies. |
